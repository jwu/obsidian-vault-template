# Article Archiving

为本项目中的外部文章建立或完善档案，输出到 `80-archive-档案库/Article-文章/`。文章档案的目标是保留可靠来源，并以贴近原文论述逻辑的方式提炼核心内容；不是机械复制全文，也不加入档案整理者的延伸判断。应与同目录已有文章的结构、语气和信息密度保持一致。

## When to use

在以下情况使用本技能：
- 用户提供文章、博客、新闻或长帖链接，要求「加入文章库」「建档」「整理」或「总结」
- 用户要求补充既有文章的作者、发布日期、来源、摘要、技术细节或相关链接
- 用户希望从文章中提取方法、实现思路、工作流或可执行结论
- 用户希望将文章与库内已有的人物、技术、应用、论文或其他文章关联

不用于：
- 论文（使用 `paper-archiving`）
- 书籍（使用 `book-archiving`）
- 单纯为某个技术、应用、组织或人物建档（使用对应 archiving skill）
- 仅需翻译、润色或回答文章内容，且不要求在知识库中留档

## References

开始前优先读取：
- `../../../99-system/templates/Article Template.md`

## Output

文章档案统一放在：
- `80-archive-档案库/Article-文章/`

默认要求：
- 笔记必须包含 `created:`、`description:` 和 `tags:` 属性，并优先使用 `[[Article Template]]`
- 已知发布日期时，文件名使用 `(YYYY-MM-DD) Article Title.md`
- 若只能确认年份，使用 `(YYYY) Article Title.md`；无法可靠确认日期时使用文章常用标题，不伪造日期
- 标题以文章页面或作者给出的正式标题为准；必要时可在 `aliases` 保留常见简称或链接标题
- 文章正文以简洁中文整理，保留英文术语、代码和原始专名的准确写法
- 正文依次使用「核心观点」「段落内容」「总结」三个二级标题，并在有已确认关联时于末尾加入「相关」；不保留空章节

## Rules

- 默认使用简洁中文；忠实保留原文的事实、条件、论证关系和不确定性，不把作者观点写成已证实结论
- 不加入整理者的延伸判断、个人启发或面向用户的推断；仅整理原文可支持的内容
- 优先小步补充既有笔记，避免覆盖原有摘录、批注和用户判断
- 编辑 Markdown 时保持 Obsidian 兼容；嵌套列表使用 4 空格缩进
- 引用文件夹时使用 `文件夹名/`，不要使用文件夹 wikilink
- 创建、移动或重命名文章笔记时，使用 `obsidian vault=work ...`；创建后再使用 `edit` 写入内容
- 不因文章提及某技术、人物或工具而自动新建其档案；只有用户明确要求时才扩展归档范围
- 正文中已经存在对应档案的实体应使用 wikilink；没有对应档案但有可靠官方链接时使用 Markdown 外链
- 文章档案默认不评分。用户明确要求评分时，使用 `99-system/rating.md` 的 `1~7` 整数制

## Workflow

### 1. 确认文章身份与已有笔记

先确认链接确实指向目标文章，而非主页、搜索页、登录页、聚合页或同名文章。记录：
- 正式标题
- 作者或发布组织
- 原始 URL
- 发布日期
- 摘要 / description

随后在 `80-archive-档案库/Article-文章/` 搜索同名、近似标题、URL 和别名：
- 已有笔记：更新原笔记
- 不存在：创建新笔记
- 可能为同一文章的转载、修订版或翻译：先确认与用户意图，避免制造重复档案

### 2. 获取并核验原文

按来源选择工具：
- 普通网页、博客和文档页：优先执行 `defuddle parse <url> --md`
- 需要元数据时：使用 `defuddle parse <url> -p title`、`author`、`published`、`description`
- 直接 `.md` 文件：使用 `webfetch`
- GitHub 链接：使用 `webfetch`，以仓库或 PR 的官方信息为准

检查提取结果是否为正文，而非导航、验证码、登录提示或无关内容。来源不可访问或元数据缺失时，保留已确认字段，并在交付中说明；不要依据 URL、页面路径或猜测补全作者、日期和技术细节。

### 3. 提炼而非复制

正文固定按以下顺序组织，整体贴近原文的论述顺序与重心：

```md
## 核心观点

## 段落内容

## 总结

## 相关
```

- `## 核心观点`：用一段客观摘要说明文章讨论什么，以及作者提出的核心论点、方法或结论；不写「为什么值得留档」、个人关联或延伸评价。
- `## 段落内容`：按原始内容的分段顺序展开主体内容。
    - 视频、演讲或播客：优先沿用原视频已有的章节或叙事分段；原视频没有分段时，再根据内容的论述转折自行划分。无论采用哪种方式，每个 `###` 标题都必须标明时间区间，格式为 `### 00:00–01:28 - 分段标题`；时间区间须来自视频章节、字幕或可核验的播放位置，不得伪造或写成「未标注时间」。
    - 文章：优先沿用原文已有的章节、小标题或明确段落划分；原文没有分段时，再根据内容的论述转折自行划分连续段落单元，并用有语义的 `###` 标题按序说明。不得改变原意。
    - 技术内容优先保留问题、关键机制、设计取舍、限制与结论；工作流或经验内容保留步骤、决策标准、边界条件与结果；新闻或观点内容清楚区分可核验事实、作者判断与引用来源观点。
- `## 总结`：以一段或少量要点客观归纳全文的主要结论、方法或限制；不得加入整理者判断或行动建议。
- `## 相关`：放在末尾，只列与文章存在直接关系的已确认 wikilink 或可靠外链；没有相关条目时省略整个章节。
- 原文中的代码、公式、表格仅保留理解机制不可替代的最小片段，并注明必要上下文。

不要为了凑内容逐段翻译或大段转载原文，也不要保留空章节。

### 4. 生产或更新笔记

新建笔记时：
1. 先检查目标路径是否存在
2. 用 `obsidian vault=work create name=<name> path='80-archive-档案库/Article-文章'` 创建空笔记
3. 再用 `edit` 写入内容

frontmatter 优先使用已确认且有长期检索价值的字段：

```yaml
---
created: YYYY-MM-DD
template: "[[Article Template]]"
author: 作者名或 "[[已有的人物档案]]"
url: https://example.com/article
published: YYYY-MM-DD
description: 一句话原始摘要或准确概述
tags:
  - article
  - 主题标签
aliases:
  - 常见别名
---
```

填写规则：
- `created` 是本笔记创建日期，不等同于文章发布日期
- `author` 仅在库内已有明确人物档案时使用 wikilink，否则保留纯文本
- `published` 使用页面的发布日期；日期不完整时不要伪造完整日期
- `description` 为必填字段，优先采用页面 meta description；没有时用一句准确概述
- `tags` 为必填字段，至少包含 `article`，其余用稳定、可检索的主题标签，不堆砌
- `aliases` 仅在确有常用简称、旧标题或译名时写入
- 未确认的非必填字段直接省略，不保留空字段；更新已有笔记时保留用户已有的有效属性和内容

文章正文从 `## 核心观点` 开始，随后依次写「段落内容」「总结」与按需出现的「相关」。原始文章来源统一保留在 frontmatter 的 `url` 属性；正文只有在需要说明多个来源、镜像或版本差异时，才列出相关 Markdown 外链。文章若与已有笔记存在直接关系，应在末尾「相关」节列出 wikilink 或可靠外链。

### 5. 补全内部关联

逐项扫描正文中提到的技术、框架、库、协议、应用、人物、组织、论文、书籍和文章：
1. 在 `80-archive-档案库/` 中确认已有对应笔记 → 使用 `[[wikilink]]`
2. 没有笔记但原文给出明确、可靠的官方或一手链接 → 使用 Markdown 外链
3. 其余保留纯文本

只链接能够确认是同一实体的内容，不为泛化词汇、模糊别名或不确定关系强行链接。

### 6. 校验

完成前检查：
- 标题、作者、日期、URL 均来自可靠页面信息，或已保守省略
- 新文件路径与命名符合文章库惯例，且没有重复条目
- Markdown 与 YAML 合法；表格中的 `[[wikilink|alias]]` 写成 `[[wikilink\|alias]]`
- 「核心观点」准确概括文章主题、核心论点或方法，而不是泛泛复述或添加延伸评价
- 「段落内容」优先采用原始内容已有分段；无原始分段时才按论述转折自行划分。视频的每个分段标题均使用可核验的时间区间，文章内容对应其章节或段落单元
- 「总结」客观归纳原文结论、方法或限制；「相关」位于末尾且不为空
- 已完成正文实体的内部链接扫描
- 未将作者观点、实验结果或推测误写为客观事实，也未混入整理者判断

## Ambiguity handling

- 页面日期有更新日和发布日期：优先记录发布日期；只有更新日时可记录更新日，并在正文注明
- 文章有修订版：优先记录用户提供的版本；如两版均有独立价值，先向用户确认是否分别建档
- 作者、出版组织或技术结论存在冲突：优先原文、官方仓库或一手资料；无法消解时保守描述冲突
- 提取内容不完整：不以二手摘要填充成完整分析，必要时请用户提供全文、视频字幕或替代来源；视频无法取得足以标注各段时间区间的内容时，不完成「段落内容」的整理
- 用户仅提供 URL、但未指定深度：默认建立包含完整必填元数据、「核心观点」、按原文顺序整理的「段落内容」、「总结」与按需出现的「相关」的中等密度档案

## Quality bar

- 一篇档案应让读者通过「核心观点」「段落内容」和「总结」快速回答：文章讨论什么、作者提出哪些核心论点或方法、其适用条件或限制是什么
- 优先沉淀原文中的方法、设计取舍和限制，而不是链接堆积、内容复述或延伸发挥
- 事实、原作者观点和引用来源的观点应可区分；档案中不加入整理者判断
- 新笔记应自然接入既有档案网络，但不为链接数量牺牲准确性
- 内容应可持续补充，不以一次性百科式穷举为目标

## Delivery

完成后，简要说明：
- 新建或更新的文章笔记路径
- 已补充的元数据和核心内容
- 建立的关键内部关联
- 仍缺失或待确认的信息（如发布日期、作者、全文访问等）
